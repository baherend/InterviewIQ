# InterviewIQ — Local Setup (Windows / Docker)

This document covers local environment configuration, database migrations,
the user-role and organization/membership data foundation, backend RBAC
enforcement, the frontend role-based routing/dashboard foundation, and the
System Admin user-management foundation (account status, role changes). It
does not cover organization-owned question banks, invitation/approval
workflows, or real AI model integration — those are handled in later
phases.

## 1. Configure environment variables

1. Copy the example file to a real `.env` in the project root:
   ```
   copy .env.example .env
   ```
2. Open `.env` and replace the placeholder values, at minimum:
   - `POSTGRES_PASSWORD` — pick a real local password.
   - `DATABASE_URL` — update the password portion to match `POSTGRES_PASSWORD`.
   - `JWT_SECRET_KEY` — generate a real random value, e.g.:
     ```
     python -c "import secrets; print(secrets.token_urlsafe(48))"
     ```
3. **`.env` must never be committed.** It is git-ignored. Only
   `.env.example` (placeholders only) is tracked in version control.

The backend will refuse to start with a clear error if `DATABASE_URL` or
`JWT_SECRET_KEY` is missing — it no longer falls back to a hardcoded secret.

## 2. Start Docker Desktop

Docker Desktop must be running before using `docker compose`. Start it from
the Windows Start Menu and wait until it reports "Running" before continuing.

## 3. Start the stack

From the project root:
```
docker compose up --build
```

This builds and starts four services: `db` (PostgreSQL), `backend`
(FastAPI), `frontend` (Vite dev server), and `nginx` (HTTPS reverse proxy).

## 4. Check container status

In another terminal:
```
docker compose ps
```
or
```
docker ps
```

## 5. Stop the stack

```
docker compose down
```

This stops and removes the containers **without** deleting data volumes.
Do not add `-v` to this command — that would delete the PostgreSQL data and
uploaded interview recordings.

## Where data is persisted

- **PostgreSQL data** — named Docker volume `postgres_data`, mounted at
  `/var/lib/postgresql/data` inside the `db` container.
- **Uploaded interview recordings** — named Docker volume `uploads`, mounted
  at the path set by `UPLOAD_DIR` (default `/app/storage/uploads`) inside the
  `backend` container. This replaced the previous `/tmp/uploads` path, which
  is not a durable location on all platforms.

Both volumes survive `docker compose down`. They are only removed by
`docker compose down -v` or `docker volume rm`, which should not be run
without a clear reason.

## Database migrations (Alembic)

As of this phase, **Alembic is the single authoritative source of the
database schema.** The application no longer creates tables on startup — a
database must be migrated with Alembic before the backend will start
against it. If the backend finds the schema missing (e.g. a brand-new,
unmigrated database), it fails fast at startup with a clear error telling
you to run `alembic upgrade head`, instead of silently creating tables.

All commands below are run **inside the running backend container**, from
its `/app` working directory (which is what `alembic.ini`'s
`script_location = alembic` is relative to):

```
docker compose exec backend bash -c "cd /app && alembic <command>"
```

### First-time setup / a brand-new database

Before starting the backend against a database that has never been
migrated, run:
```
docker compose exec backend bash -c "cd /app && alembic upgrade head"
```
This creates the `users`, `questions`, `interviews`, and `results` tables
(and the `alembic_version` bookkeeping table). Only after this succeeds
should the backend be started.

### Check the current revision

```
docker compose exec backend bash -c "cd /app && alembic current"
```

### Upgrade an existing database to the latest migration

```
docker compose exec backend bash -c "cd /app && alembic upgrade head"
```
Safe to run repeatedly — Alembic no-ops if already at `head`.

### Create a new migration (future schema changes)

```
docker compose exec backend bash -c "cd /app && alembic revision --autogenerate -m 'short description'"
```
The backend container does **not** bind-mount the source tree, so the
generated file is written inside the container's filesystem, not the host
repo. Copy it out before it can be reviewed or committed:
```
docker cp <backend-container-id>:/app/alembic/versions/<generated_file>.py backend/alembic/versions/
```
(Find the container id with `docker compose ps -q backend`.)

**Always manually review an autogenerated migration before applying it.**
Alembic's autogenerate is a starting point, not a guarantee — check that it
only contains the change you intended, with no accidental drops, renames, or
unrelated operations, before running `alembic upgrade head`.

### Migration safety rules

- **Never run `alembic downgrade` against local data you want to keep,
  without a verified backup first.** Downgrades in this project are
  destructive (they drop tables/columns) by design — there is no
  non-destructive way to undo a `CREATE TABLE`.
- **Never run `docker compose down -v`** — it deletes the `postgres_data`
  volume (and `uploads`), destroying all local data regardless of migration
  state.
- **All migration files under `backend/alembic/versions/` must be committed
  to Git.** They are no longer git-ignored (as of this phase) — the schema
  history must travel with the code.
- The root `.env` (containing `DATABASE_URL` and other secrets) remains
  private and git-ignored; never put real credentials in a migration file
  or in this documentation.

## User roles

The `users` table has a `role` column with exactly five allowed values:
`system_admin`, `student`, `company_admin`, `interviewer`, `candidate`.
These are enforced at the application layer (a Python `Enum` in
`backend/app/models/user.py`), not a Postgres-native `ENUM` type, so future
changes stay simple Alembic migrations rather than type-alteration
migrations.

**Public registration (`POST /api/auth/register`) always creates a
`student` account.** The request schema has no `role` field, so a client
cannot influence this — even if a `role` value is included in the request
body, it is silently ignored and the account is still created as `student`.
There is no public API for creating `system_admin`, `company_admin`,
`interviewer`, or `candidate` accounts. The role is exposed through
`GET /api/auth/me` and the login/register response.

As of this phase, the backend also **enforces** authorization based on
this role for a small set of endpoints — see "Backend authorization
(RBAC foundation)" below. Frontend role-based dashboards and route guards
are still not implemented; the frontend hiding a link is not a security
boundary — the backend is.

### Creating a local system admin

Privileged roles are never created through the public API. To create a
local `system_admin` for development, run the script manually inside the
backend container:

```
docker compose exec \
  -e ADMIN_EMAIL=admin@example.com \
  -e ADMIN_NAME="System Admin" \
  -e ADMIN_PASSWORD=<a-real-local-only-password> \
  backend python scripts/create_system_admin.py
```

Or with CLI arguments instead of environment variables:
```
docker compose exec backend python scripts/create_system_admin.py \
  --email admin@example.com --name "System Admin" --password <password>
```

- The password is read from `ADMIN_PASSWORD` / `--password` — never
  hardcode it anywhere, and it is never printed by the script.
- Safe to re-run: if that email already belongs to a `system_admin`, the
  script no-ops. If it belongs to a different existing user, the script
  refuses to modify it and exits with an error rather than overwriting
  anything.
- This script is **not** run automatically at application startup and has
  no HTTP endpoint equivalent — it must be run manually, on purpose, by
  someone with local access to the backend container.

## Organizations and membership (foundation only)

**Global user role and organization membership role are two separate
concepts — do not confuse them.**

- **Global user role** (`users.role`): `system_admin`, `student`,
  `company_admin`, `interviewer`, `candidate`. This is platform-wide and
  set once at account creation (see "User roles" above). Creating or
  joining an organization never changes it.
- **Organization membership role** (`organization_memberships.membership_role`):
  `owner`, `admin`, `interviewer`, `candidate`. This only describes a
  user's standing *within one specific organization* and is stored per
  `(organization_id, user_id)` pair — the same user can only have one
  membership row per organization (enforced by a unique constraint).

A user's global role and their membership role in any given organization
are independent. For example, a `student` can be the `owner` of an
organization without their global role ever changing to `company_admin`.

### Organization statuses

`pending` (default for every newly created organization), `active`,
`suspended`. Nothing in this phase transitions an organization between
these states automatically — that workflow is not implemented yet.

### How organization creation currently works

- **Only `system_admin` may create an organization** — `POST
  /api/organizations`. There is no public/self-service organization
  registration.
- The request must include `owner_user_id` (an existing, **active** user's
  id — an inactive/suspended user is rejected with 400). The creator does
  **not** automatically become the owner — the owner is whoever
  `owner_user_id` points to, which may or may not be the caller.
- The organization is created with status `pending`, and exactly one
  `owner` membership is created for `owner_user_id`, in a single database
  transaction (if the membership insert fails, the organization insert is
  rolled back too — no orphaned organization is left behind).
- The owner's global `role` is never modified by this process (a `student`
  can own an organization and stay a `student`).
- Read access: `system_admin` can list/view any organization; any other
  user can only see organizations where they have an **active**
  membership. A non-member requesting a private organization gets the same
  404 as a nonexistent one (existence is not leaked).

### System Admin organization management (Phase 2B)

All under `/api/organizations`, reusing the same router as the read
endpoints above (not a separate admin router — the list/detail endpoints
already branch on caller role, so adding a second router would only
duplicate that branching):

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/organizations` | system_admin: paginated + `q` (name/slug search) + `status` filter + owner/member-count enrichment. Non-admin: unchanged — plain list of the caller's own active, non-suspended memberships. |
| `GET` | `/api/organizations/{id}` | system_admin: enriched detail (owner + member count). Active member: unchanged plain detail. |
| `POST` | `/api/organizations` | system_admin only, as above. |
| `PATCH` | `/api/organizations/{id}` | system_admin only. Edits `name`/`slug`/`description` only — the schema has no `status` field, so a client including `"status"` in this request body is silently ignored, never applied. Duplicate slug rejected. Owner and memberships untouched. |
| `PATCH` | `/api/organizations/{id}/status` | system_admin only. See transition policy below. |
| `GET` | `/api/organizations/{id}/members` | Extended in Phase 2C — see "Organization membership management" below. |

No organization deletion or owner replacement — still out of scope.
Membership-mutation endpoints (adding/removing members, editing a member's
role) were added in Phase 2C — see below.

#### Status transition policy

```
pending   -> pending, active, suspended
active    -> active, suspended                (NOT pending — no "un-approve")
suspended -> suspended, active                 (NOT pending — no "reset")
```

Setting the current status again (e.g. `active` -> `active`) succeeds as a
no-op (200, idempotent) — SQLAlchemy won't even emit an `UPDATE` if the
value is unchanged, so `updated_at` correctly stays the same in that case.
Any transition not listed above (`active -> pending`, `suspended ->
pending`) is rejected with 400 and a clear message naming both the current
and requested status. Status changes only ever write the `status` column
— they never touch `organization_memberships` rows or any user's global
`role`.

## Organization membership management (Phase 2C)

Adds safe membership management on top of the Phase 2B foundation: listing
members (enriched/paginated), adding an existing active user, changing a
membership's role, activating/deactivating a membership, and removing a
non-owner membership — all under strict server-side authorization. **No
migration was needed** — every field this phase uses
(`organization_memberships.membership_role` / `.is_active`, plus the
existing unique `(organization_id, user_id)` constraint) already existed
from the original schema.

### Endpoints

All under `/api/organizations/{organization_id}/members`:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `.../members` | **Changed in Phase 2C.** Always returns the enriched, paginated `{items, total, page, page_size}` shape (each item includes a nested `user: {id, name, email, role, is_active}` summary) — previously a plain array of bare membership rows. Params: `q` (search member name/email), `membership_role`, `is_active`, `page`, `page_size`. Read access unchanged: system_admin or any active member of any role. |
| `POST` | `.../members` | Add an existing active user as `admin`, `interviewer`, or `candidate` (never `owner`). Body: `{"user_id": <int>, "membership_role": "<role>"}` — `organization_id` always comes from the URL, never the body. Rejects a nonexistent or inactive target user (404 / 400), and rejects a user who already has any membership (active or inactive) in this organization (400). |
| `PATCH` | `.../members/{membership_id}/role` | Body `{"membership_role": "<admin\|interviewer\|candidate>"}`. Owner cannot be assigned (schema-level validation) or targeted (see owner invariants below). |
| `PATCH` | `.../members/{membership_id}/status` | Body `{"is_active": true\|false}`. Only ever writes `organization_memberships.is_active` — never `users.is_active` (a different field with different semantics: membership status vs. global account status). |
| `DELETE` | `.../members/{membership_id}` | Removes the membership row only — the `User` row is never touched. |

### Authorization

- **system_admin**: full access to every action above, on any organization
  (including `suspended` ones — the one caller for whom the
  suspended-organization block does not apply).
- **Organization owner or admin** (active membership): full access to
  every action above, subject to the owner invariants and self-management
  rule below, and subject to the existing suspended-organization policy
  (blocked while `suspended`; `pending` is fine, same as every other
  organization endpoint).
- **Interviewer / candidate members**: read-only — they can still call
  `GET .../members` (unchanged from Phase 2B: any active member), but
  every mutating endpoint rejects them with 403.
- **Non-members** (including a `company_admin` with no active membership
  in this organization — global role is never used as the organization
  authorization source, only `system_admin` bypasses membership
  entirely): 404 on every endpoint under `.../members`, identical to a
  nonexistent organization. This matches `require_organization_access`'s
  existing privacy-preserving behavior from Phase 1E/2B.

New dependency `require_membership_manager` in
`backend/app/auth/permissions.py` implements the owner/admin-or-system_admin
check above and returns `(current_user, caller_membership)` — the caller's
own membership row (or `None` for a system_admin who isn't themselves a
member), used by the self-management rule below.

**Fix to `require_organization_roles` (first wired to a route in this
phase):** previously, a caller with no membership at all in an *existing*
organization received 403 (which confirms the organization exists to any
authenticated non-member) instead of the 404 that
`require_organization_access` already used for the same situation. Since
nothing called `require_organization_roles` before Phase 2C, this had zero
effect on any shipped endpoint; it's corrected now, before its first real
use — a genuine member with an insufficient role still gets 403 (they
already know the organization exists).

### Owner invariants (universal — apply even to system_admin)

Every organization always has exactly **one** active owner membership,
created only as a side effect of `POST /api/organizations` (see
"Organizations and membership" above). Through the membership-management
endpoints:

- The owner membership's role can never be changed (`PATCH .../role`
  rejects with 400 if the target is the owner).
- The owner membership can never be deactivated or removed (`PATCH
  .../status` and `DELETE` both reject with 400).
- No membership can ever be assigned `owner` (schema-level validator on
  `POST` and `PATCH .../role` — `owner` is not an accepted value).
- Owner replacement is out of scope for this phase — there is no way to
  transfer ownership through any endpoint.

### Self-management rule

An organization **admin** cannot deactivate or remove their own admin
membership through `PATCH .../status` or `DELETE` (400, "ask another
owner/admin or a system admin") — the safer default, since an admin could
otherwise strand an organization admin-less if they were the only one.
**system_admin bypasses this** (can deactivate/remove anyone, including an
admin acting on their own row via a separate system_admin session). An
owner is unaffected by this rule since owner rows are already immutable
per the invariants above. Admin-to-admin management (one admin managing a
*different* admin's membership) is unrestricted.

### What is not implemented yet

- No organization deletion or owner-replacement endpoints.
- No public organization signup.
- No organization-owned/company question banks yet — questions remain a
  single global table.
- No full RBAC framework (`require_permission`, permission matrix,
  tenant/organization-context middleware) — authorization in this phase is
  a small number of explicit, inline checks (`role == system_admin`, "has
  an active membership in this organization", "has an owner/admin
  membership"), not a reusable system.
- No organization switcher in the frontend. System Admin has a full
  Members section inside `/admin/organizations`. A minimal company-side
  (owner/admin-facing) invitation UI now exists on `/company` (Phase 2D —
  see below); a full company-side membership-editing UI (role changes,
  deactivate/remove) is still System-Admin-only.

## Organization invitations and onboarding (Phase 2D)

Adds a full invitation lifecycle on top of the Phase 2C membership
foundation: an authorized manager invites a person by email into an
organization; the recipient accepts by attaching the invitation to an
existing account with a matching email, or by registering a brand-new
account through a controlled flow. **No real email is sent** — an
invitation's one-time acceptance link is returned directly in the API
response and displayed in the UI for manual delivery.

### Schema

New table `organization_invitations` (migration `7c6f3df24fbd`, descends
directly from `5112e9dff333` — no other table was touched): `id`,
`organization_id`, `email` (always normalized lowercase), `membership_role`
(`admin` | `interviewer` | `candidate` — never `owner`), `token_hash`,
`status` (`pending` | `accepted` | `revoked` | `expired`, plain string,
same pattern as `organizations.status`), `expires_at`, `created_by_user_id`
/ `accepted_by_user_id` (nullable, `ON DELETE SET NULL`), `created_at`,
`accepted_at`. A partial unique index
(`uq_org_invitations_pending_org_email`, `WHERE status = 'pending'`)
enforces "at most one pending invitation per organization+email" at the
database level, while still allowing a fresh invitation for the same
organization+email once the old one is accepted, revoked, or expired.

### Token security

- Raw tokens are generated with `secrets.token_urlsafe(32)` (256 bits of
  entropy) — see `backend/app/auth/invitation_tokens.py`.
- Only a SHA-256 hex digest (`token_hash`) is ever persisted; the raw
  value is returned exactly once, directly in the creation/rotation API
  response (`InvitationCreatedResponse.token` / `.accept_url`), and is
  never included in any list response or logged.
- **Expiration: 168 hours (7 days)** — `INVITATION_EXPIRE_HOURS` in
  `backend/app/config.py`, matching this app's existing 7-day JWT-expiry
  default for a consistent mental model. Fixed server-side; not
  client-configurable through the API.
- **Lazy expiry, not a scheduler**: no background worker exists in this
  phase. Every endpoint that reads or mutates an invitation (list, create,
  revoke, rotate, inspect, accept, register-and-accept) first transitions
  any `pending` row whose `expires_at` has passed to `expired` before
  doing anything else — so behavior is always deterministic and never
  depends on when a sweep last ran.
- A locally generated acceptance link looks like
  `https://localhost/invitations/accept?token=<raw-token>`
  (`FRONTEND_PUBLIC_URL` in `.env.example` / `config.py`).

### Authorization matrix

| Caller | Create / List / Revoke / Rotate | Notes |
|---|---|---|
| `system_admin` | Any organization, any status (including `suspended`) | Global role, always bypasses membership |
| Active `owner` membership | Own organization only, `pending`/`active` only | `suspended` blocks all four actions |
| Active `admin` membership | Own organization only, `pending`/`active` only | Same as owner |
| Active `interviewer`/`candidate` membership | None | 403 |
| Non-member (including `company_admin` global role with no active membership) | None | 404, identical to a nonexistent organization |

Reuses `require_membership_manager` (Phase 2C) unchanged — invitation
management requires exactly the same standing as membership management
(system_admin, or active owner/admin), so no new authorization primitive
was needed.

### Invitation role policy

Only `admin`, `interviewer`, `candidate` are invitable — enforced by a
Pydantic validator on `InvitationCreate`, so `owner` and `system_admin` are
rejected (422) before the request ever reaches the router. Acceptance
always creates exactly the membership role stored on the invitation — the
invited user's **global** role is a separate decision (see below) and is
never touched by accepting as an existing user.

### Existing-account acceptance — `POST /api/invitations/accept`

Authenticated (any active user). The current account's email must match
the invitation's email case-insensitively — **no system_admin bypass**,
since this is the invited person acting on their own behalf, not a
management action. Creates the membership with the invitation's role and
`is_active=true`, marks the invitation `accepted`, all in one transaction.
The invited user's global role is never changed.

### New-account registration — `POST /api/invitations/register-and-accept`

Public (no auth required). Email comes **exclusively** from the
invitation row the token resolves to — the request body has no `email` or
`membership_role` field, so neither can be client-supplied or overridden.
Global-role mapping for the brand-new account:

| Invitation `membership_role` | New account's global `role` |
|---|---|
| `admin` | `company_admin` |
| `interviewer` | `interviewer` |
| `candidate` | `candidate` |

This is the first and only creation path for `company_admin` accounts in
this app — public `/api/auth/register` remains `student`-only, unchanged.
Password is hashed with the existing `hash_password` utility (same bcrypt
scheme as normal registration); no new password-strength rule was added
beyond what public registration already required (none, today). On
success, the response auto-logs the new user in with the same `Token`
shape and `create_access_token` call public registration already uses —
not a new, inconsistent auth pattern for this one flow.

### Suspended-organization behavior

- `suspended`: owner/admin invitation actions (create/list/revoke/rotate)
  are blocked (403); only `system_admin` may still manage invitations.
  Acceptance (existing-account or new-account) is blocked unconditionally
  for everyone, including system_admin — `GET /invitations/inspect` also
  reports `valid: false, reason: "organization_suspended"` for a token
  belonging to a suspended organization.
- `pending` / `active`: full invitation behavior, no special-casing.
- Changing an organization's status never automatically modifies any
  invitation.

### Revoke semantics

Only a `pending` invitation can be revoked. An `accepted` or `expired`
invitation returns 400 if a revoke is attempted. Revoking an
already-`revoked` invitation is treated as an idempotent no-op (200,
unchanged) rather than an error. Revoking never touches any existing user
or membership row.

### Frontend

- **Public acceptance page** — `/invitations/accept?token=...`
  (`frontend/src/pages/InvitationAccept.jsx`), deliberately unguarded (no
  `ProtectedRoute`/`PublicOnlyRoute` wrapper) since it must work for both
  an anonymous visitor and an already-authenticated user. Handles every
  required state: loading, invalid/not-found, expired, revoked,
  already-accepted, suspended-organization, valid (branching further into
  existing-account-logged-in / existing-account-needs-login /
  email-mismatch / new-account-registration), and a success state that
  redirects to the correct role home. The raw token is stripped from the
  visible URL immediately after a successful accept/register (`useSearchParams`
  replace) — it is never written to `localStorage`.
- **System Admin UI** — `/admin/organizations` organization detail modal
  gained an Invitations section: list with search/status filter/pagination,
  create (email + role), one-time acceptance-link display with a copy
  button and an explicit "shown once, not retrievable again" warning, and
  revoke for pending invitations.
- **Company-side UI** — a minimal Invitations card on `/company`, shown
  only when the caller's own membership role is `owner`/`admin` and their
  organization isn't suspended (mirroring, not replacing, backend
  authorization). Supports create (with the same one-time-link warning)
  and revoke; deliberately no search/filter/pagination, matching the
  task's "keep it minimal" allowance. No broad user directory is exposed —
  invitations are addressed by email only.

### What is not implemented yet

- No real outbound email — every acceptance link is local/manual-delivery
  only, by design for this phase.
- No owner invitations, no owner replacement via invitations.
- No company-side membership-role editing UI (still System-Admin-only —
  see "Organization membership management (Phase 2C)").
- No resend-with-email — "rotate" (`POST .../invitations/{id}/rotate`)
  generates and returns a new one-time link for a still-pending
  invitation instead; the old token stops working immediately since its
  hash is overwritten.

## Backend authorization (RBAC foundation)

As of this phase, authorization is enforced **server-side**, backed by the
database — not by the frontend hiding links, and not by anything in the
JWT beyond identifying who the caller is.

**Global user role vs. organization membership role — reminder:** these
remain two separate concepts (see "Organizations and membership" above).
A global role (`system_admin`, `student`, `company_admin`, `interviewer`,
`candidate`) is checked with `require_global_roles(...)`. An organization
membership role (`owner`, `admin`, `interviewer`, `candidate`) is checked
separately with the organization-membership helpers. Nothing merges them.

### How it works

- `GET /api/auth/me` and every other authenticated endpoint now depend on
  a database-backed `get_current_user`, which decodes the JWT, then loads
  the `User` row fresh from PostgreSQL on every request. The JWT itself
  carries no role claim and is never treated as authorization truth — only
  identity (`sub`, i.e. the user id). A token for a user that no longer
  exists is rejected with 401.
- Reusable authorization helpers live in `backend/app/auth/permissions.py`:
  - `require_global_roles(*roles)` — global-role gate (e.g. system_admin
    only).
  - `get_active_membership(db, organization_id, user_id)` — plain lookup
    of the caller's active membership row, if any.
  - `require_organization_access(...)` — requires system_admin OR an
    active membership in the given organization; also enforces the
    suspended-organization policy below.
  - `require_organization_roles(*membership_roles)` — like the above, but
    additionally requires the active membership's role to be one of the
    given values (or system_admin, which always passes). First wired to a
    route in Phase 2C (organization membership management); see
    "Organization membership management (Phase 2C)" above for the
    404-vs-403 fix that shipped alongside its first real use.
  - `require_membership_manager(...)` (Phase 2C) — requires system_admin
    or an active owner/admin membership; returns `(current_user,
    caller_membership)` for the membership-management endpoints' owner
    invariants and self-management rule.
- These are deliberately small, explicit dependency functions — not a
  permissions matrix, not JSON permissions, not tenant middleware.

### Organization access rules

- `system_admin` can access any organization and any membership list,
  regardless of status.
- Everyone else needs an **active** membership in that specific
  organization. An inactive membership behaves as if it doesn't exist —
  it does not authorize access.
- A `student` (or any other global role) has **no** organization access
  purely from their global role — access always comes from membership
  (except system_admin).
- **Suspended organizations**: blocked for normal (non-system_admin)
  members across every organization endpoint — `GET /organizations`
  (excluded from the list), `GET /organizations/{id}` and `/members`
  (403), and `GET /organizations/me/memberships` (excluded from the list,
  for *all* callers including system_admin, since that endpoint reflects
  personal active-membership standing rather than an admin view).
  system_admin can still read a suspended organization directly via
  `GET /organizations` (full list) and `GET /organizations/{id}`.
- **Pending organizations**: readable by their active members and by
  system_admin — pending is *not* treated as blocked, only suspended is.

### Interim question-mutation rule

`POST /PUT /DELETE /api/questions` are `system_admin`-only in this phase.
There is no organization-owned question bank yet (the table is still a
single global list), so a narrower per-company rule isn't meaningful
either — `system_admin`-only is the narrowest safe interim rule until
question-bank isolation is designed. `GET /api/questions` remains open to
any authenticated user, unchanged.

### What is still deferred

- No generic permissions framework (`require_permission`, a permissions
  matrix, tenant/organization-context middleware).
- No company-owned/organization-scoped question banks — questions remain a
  single global table, gated only by the interim system_admin-only rule
  above.
- No organization membership-management endpoints (adding/removing
  members, changing membership roles) or invitation/approval workflows —
  global user-role management now exists (see "System Admin user
  management" below), but organization membership is still untouched by
  any endpoint besides the owner membership created at organization
  creation time.

## System Admin user management

### Account active/inactive behavior

`users.is_active` (boolean, default `true`) is the only account-status
field. **An inactive (suspended) user cannot log in**
(`POST /api/auth/login` returns 403 `"This account has been suspended"`
even with correct credentials), **and an inactive user's existing JWT
stops working immediately** — `get_current_user` (used by every
authenticated endpoint, including `/api/auth/me`) checks `is_active` on
every request and rejects with 403 if false. There is no separate
token-blocklist or refresh-token-invalidation mechanism — none is needed,
since the database is re-checked on every request regardless of how old or
new the token is.

**Why 403, not 401, for a suspended account**: the token is genuinely
valid and correctly identifies a real user — this is an authorization
decision ("this identity is not currently permitted"), the same class of
failure as a role/membership check failing elsewhere in this app, not an
authentication failure. 401 is reserved for "there is no valid identity
here at all" (missing/invalid token, or a token for a user that no longer
exists).

### System Admin user-management routes

All under `/api/admin/users`, **system_admin only**:

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/admin/users` | Paginated list; `q` (search name/email), `role`, `is_active`, `page`, `page_size` |
| `GET` | `/api/admin/users/{id}` | Full detail + organization-membership summary |
| `PATCH` | `/api/admin/users/{id}/status` | Body `{"is_active": true\|false}` |
| `PATCH` | `/api/admin/users/{id}/role` | Body `{"role": "<one of the five UserRole values>"}` |

No user deletion, password reset, bulk actions, or public role editing
exist. `password_hash` is never returned by any of these endpoints.

### Last-active-system_admin protection

Both the status and role endpoints refuse to reduce the number of active
`system_admin` accounts to zero — whether that's an admin suspending/
demoting someone else who happens to be the last one, or an admin
suspending/demoting **themselves** as the last one. Both return 400 with a
clear message (`"Cannot suspend the last active system_admin."` /
`"Cannot change role: this is the last active system_admin."`) rather than
silently succeeding or crashing. This check counts globally (active
`system_admin` rows, regardless of who is making the request) — there is
no way to lock the platform out of admin access through these two
endpoints.

### Role changes do not touch organization memberships

Changing a user's global role via `PATCH /api/admin/users/{id}/role` only
writes `users.role`. It never creates, deletes, or modifies any
`organization_memberships` row — a user's standing inside any organization
they belong to is completely unaffected by a global role change (and vice
versa; see "Organizations and membership" above for the general
global-role-vs-membership-role distinction).

## Frontend routing and dashboards

**Frontend route guards are UX only — they are not a security boundary.**
Every route below is also independently re-checked by the backend (see
"Backend authorization (RBAC foundation)" above); a guard here exists to
send a user to a sensible page quickly, not to make the app secure. If a
frontend guard were ever removed or buggy, the backend would still reject
an unauthorized request.

### Role-home routes

| Global role | Home route |
|---|---|
| `system_admin` | `/admin` |
| `student` | `/student` |
| `company_admin` | `/company` |
| `interviewer` | `/interviewer` |
| `candidate` | `/candidate` |

`frontend/src/utils/roles.js` exports `getHomeRouteForRole(role)`, the
single source of this mapping — used consistently after login,
registration, on `/dashboard` (kept as a backward-compatible redirect),
and by the guards. **An unrecognized or missing role never defaults to
`/admin`** — it fails safe: the user is logged out and sent to `/login`.

### Route guards

`frontend/src/routes/guards.jsx`:
- `ProtectedRoute` — requires any authenticated user.
- `RoleRoute` — requires authentication AND one of a specific set of
  global roles; a role mismatch goes to `/unauthorized`, not silently
  nowhere.
- `PublicOnlyRoute` — used on `/login` and `/register`; an already
  authenticated user is redirected to their role home instead of seeing
  the form again.

All three show a stable loading screen while `/auth/me` is still
resolving — there is no flash of protected content before authentication
is confirmed, and no route guard makes its decision from `localStorage`
alone (the cached user is only an optimistic placeholder used while
`loading` is still `true`; the guards themselves gate on `loading`, not on
the cached value).

### Current dashboard status

- **Student** (`/student`) — the original, fully-functional interview
  dashboard (stats, charts, history) — unchanged, just re-routed.
- **System Admin** (`/admin`) — real organization count/list (read-only)
  and a real link to the platform question bank (`/admin/questions`);
  users management, assessments, service health, and storage/logs are
  clearly labeled "Coming soon" placeholders (no backing endpoint exists
  yet).
- **Company Admin / Interviewer / Candidate** (`/company`,
  `/interviewer`, `/candidate`) — **placeholders**. Each shows a real
  organization-membership summary (via `GET /organizations/me/memberships`
  + `GET /organizations/{id}`), with proper empty/pending/error states.
  Company Admin additionally shows a real, read-only member list (`GET
  /organizations/{id}/members` — Phase 2C: enriched `{items, ...}` shape
  with each member's name/email) and, for an owner/admin membership in a
  non-suspended organization, a minimal real Invitations card (Phase 2D:
  create/list/revoke, one-time local acceptance link). Company question
  bank, assessments, and candidate/interviewer management (including any
  membership-editing UI) are "Coming soon" — see "What is not implemented
  yet" under membership management and under invitations above.
- Public registration (`POST /api/auth/register`) always creates a
  `student` account and always lands on `/student` — there is no role
  selector anywhere in the UI, and none is sent to the backend.

## Real per-question audio analysis (Phase 3A)

The normal student interview flow (`/interview/room` → `/interview/processing`
→ `/report/:id` → `/history`) now records **one distinct answer segment per
question** and runs **real, local audio analysis** on each segment — this
replaced the `app/ai_modules/audio_module.py` random-score mock in that flow.
`app/ai_modules/audio_module.py` itself still exists and is still used by the
older, untouched `POST /api/interviews/analyze/{interview_id}` endpoint, but
nothing in the new per-question flow calls it. As of Phase 3B/3C (see below),
ASR and Answer Content Score are also real in this same normal flow. Vision
remains unchanged — still mocked in the normal flow, still real only via the
separate `/fusion-test` page (see "What this phase does NOT include" below).

### What "real" means here

Two independent, real signal sources — wired through
`backend/app/services/audio_analysis_service.py`, which wraps the existing
implementations under `InterviewIQ_AI/audio/` without changing their formulas:

- **Audio emotion classification** — the same Wav2Vec2-XLSR + BiLSTM model
  used by `/fusion-test` (`InterviewIQ_AI/audio/audio_emotion_package/`,
  trained on BAVED), run in its own dedicated virtual environment via the
  existing subprocess/JSON adapter pattern
  (`InterviewIQ_AI/fusion/adapters/base.py::run_json_component`,
  `InterviewIQ_AI/fusion/runners/run_audio_json.py`). Produces an
  `emotion_label` (Low / Neutral / High Emotion), `emotion_probabilities`,
  and `model_confidence` (`max(softmax(logits))`).
  **`model_confidence` is diagnostic model certainty only — it is
  uncalibrated (no temperature scaling, Platt/isotonic scaling, ECE, or
  Brier score exists for this model) and it is not candidate performance.**
- **Vocal delivery** — `InterviewIQ_AI/audio/audio_confidence.py`, a
  deterministic DSP heuristic over speaking rate, pause control, volume
  stability, and speech continuity, run in-process (pure numpy/wave code,
  no ML model). **This is an experimental vocal-delivery indicator, not a
  scientifically validated psychological confidence score.**
  Its composite `vocal_delivery_score` requires a transcript to score
  speaking rate — ASR/NLP is out of scope for this phase, so no transcript
  is supplied, and this composite score (and `speaking_rate_wpm`) will
  legitimately be "Not available" for most answers. The three
  transcript-independent sub-scores (pause control, volume stability,
  speech continuity) are real, computed values regardless.

Neither category is ever replaced by a random value. If real analysis fails
or the audio has no usable signal, the segment's `processing_status` is set
to `failed` or `insufficient_evidence` with a stable `failure_code` (see
`app/models/answer_segment.py::AudioFailureCode`) and a human-readable
`failure_message` — the frontend shows "Not available" with that reason,
never a fabricated 0%.

### Recording → processing flow

1. `InterviewRoom.jsx` calls `POST /interviews/start-interview`, which
   persists the ordered question sequence server-side (`InterviewQuestion`
   rows) and returns it — the UI renders only from that persisted list.
2. For each question, a **fresh `MediaRecorder`** records just that answer.
   Clicking Next stops it, uploads the resulting Blob to
   `POST /interviews/{id}/segments` (bound to `interview_question_id`, with
   `question_id`/`sequence_index` cross-validated server-side), and only
   advances once the upload is acknowledged. A failed upload keeps the
   candidate on the same question with the Blob retained in memory for
   retry — it never silently drops the answer or silently skips ahead.
3. After the last answer, `InterviewRoom.jsx` navigates to
   `/interview/processing` with just the `interview_id`.
   `Processing.jsx` calls `POST /interviews/{id}/process-audio` (marks the
   recording stage complete and queues every uploaded segment) and polls
   `GET /interviews/{id}/processing-status` until every segment reaches a
   terminal state (`completed` / `partial` / `failed` /
   `insufficient_evidence`), then navigates to `/report/{id}`.
4. Processing runs via **FastAPI `BackgroundTasks`** — this is a
   local/development-grade mechanism, **not a durable production job
   queue**. If the backend process restarts mid-analysis, an affected
   segment is left in `processing` and must be retried via
   `POST /interviews/{id}/segments/{segment_id}/retry-audio`.
5. `Report.jsx`/`History.jsx` only ever read persisted
   `InterviewQuestion` / `AnswerSegment` / `AudioAnalysis` rows — opening a
   report or the history list never re-runs any analysis. Interview-level
   audio summaries average only segments with a valid
   `vocal_delivery_score`; missing/invalid segments are never averaged in
   as zero, and an interview with no valid scores yet (or a historical,
   pre-Phase-3A interview with no segments at all) shows an honest
   "not available" state instead of a fabricated summary.

### Optional real-model test

The default backend test suite (`pytest tests/`) never loads the audio
model — the model/subprocess boundary is mocked. To actually exercise the
real model once (takes about a minute, no paid API involved):

```bash
cd backend
RUN_REAL_AUDIO_TESTS=1 <path-to-venv>/pytest tests/test_real_audio_smoke.py -v
```

### Migration

One Alembic migration,
`b4d8f2a917c3_add_interview_questions_answer_.py`, adds three new tables
(`interview_questions`, `answer_segments`, `audio_analyses`) and one
nullable column on `interviews` (`recording_completed_at`). It does not

## Real per-question ASR and vocal delivery (Phase 3B)

Every persisted `AnswerSegment` is transcribed once by the existing real
ASR implementation (`interview_iq.asr.engine.transcribe_audio`,
faster-whisper `large-v3`, Arabic), run out of process in the NLP module's
own dedicated `.venv_nlp` environment via a thin sibling wrapper
(`InterviewIQ_AI/fusion/runners/run_asr_only_json.py`) — never the
`evaluate_answer` entry point, so this step never touches claim
decomposition/Groq/BGE-M3/NLI. The resulting transcript and its status
(`ok` / `no_speech` / `too_short`) are persisted on `AudioAnalysis`
(`transcript`, `transcript_status`) and fed into the existing, unchanged
`InterviewIQ_AI/audio/audio_confidence.py::calculate_audio_confidence`
DSP formula, so `vocal_delivery_score` and `speaking_rate_wpm` (previously
always "Not available" in Phase 3A, since that formula needs a transcript
for speaking-rate scoring) are now populated whenever a segment has enough
real, transcribed speech. Formula/weights/thresholds are unchanged from
Phase 3A. Report and History detail both display the persisted transcript
and completed vocal-delivery metrics — nothing is recomputed client-side.
Migration: `c7e1a4f8b2d5_add_audio_analysis_transcript.py`.

## Real per-question Answer Content Score (Phase 3C)

For each segment, once its transcript is persisted (above), the existing
real NLP pipeline (`interview_iq.pipeline.evaluate_answer`: claim
decomposition via Groq → BGE-M3 retrieval → NLI → Precision/Coverage/
Harmonic-F scoring) runs against it via a second thin sibling wrapper
(`InterviewIQ_AI/fusion/runners/run_content_score_json.py`) that injects
the already-persisted transcript in place of `evaluate_answer`'s own ASR
call — the real faster-whisper model never runs a second time for the
same segment. The question a segment belongs to is resolved purely by
persisted foreign keys (`AnswerSegment.question_id` → `Question.id`),
never by question text or array position. `Question.nlp_reference_id`
(and, as of Phase 3D, the stable `Question.code` provisioning key — see
below) maps a question to one of the 250 documents in
`InterviewIQ_AI/nlp/interview-iq-fusion-handoff/data/refdocs/
reference_docs_250_FINAL_v1.json`; a question with no mapping persists a
typed `NO_REFERENCE_DOCUMENT` status (`answer_content_score`/`claims`
stay `null`, never a fabricated score) without ever invoking Groq. Real
BGE-M3 ranking (the `>k`-chunk retrieval path, as opposed to the common
`<=k` pass-through) was verified against the corpus's one `>10`-chunk
document (`DS-014`) as part of the Phase 3C completion fix
(`use_fp16=False` for CPU — see `chunk_cap.py`). Results persist 1:1 on
`AnswerContentAnalysis`, retries upsert by `answer_segment_id` (never
duplicate rows), and Report/History display the persisted
precision/coverage/score/claims read-only — nothing is recomputed
client-side. Migration: `d3f9a1c6e8b4_add_answer_content_analysis.py`
(plus `e7a2c4f19b6d_add_question_code.py`, Phase 3D, for stable
question-to-reference provisioning).

## HTTPS certificate note

`nginx/openssl.cnf` generates a self-signed certificate scoped to
`localhost` / `127.0.0.1` only. It intentionally does **not** hardcode a LAN
IP, since LAN IPs are specific to a given machine/network and go stale when
the machine changes networks. Accessing the app via `https://localhost`
works out of the box; accessing it via a LAN IP will show a certificate
warning. If LAN access is needed later, this should be handled with a
per-host regenerated certificate (or a dynamic/mkcert-style flow) — this is
a follow-up for a later phase, not part of this one.
